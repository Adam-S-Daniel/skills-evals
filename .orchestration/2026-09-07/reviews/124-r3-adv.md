## 2. Findings

### Blocker

**B1 — a symlinked `.claude/settings.json` now drags a fully-healthy consumer back to the 57 kB inline guidance while its fleet-memory hook stays registered. REGRESSION vs `670e1ce` and vs `main`, introduced by commit `7d46133` implementing the brief's own R2-N7, and it re-opens R2-S5's class.**

`scripts/bootstrap-status.sh:164` (new this round):

```bash
if [[ -L "$1" ]]; then
    echo "unparseable"
```

`scripts/sync.sh:849-853` turns that word into `fleet_deliver=false`, and `:892` turns *that* into `FLEET_MODE=full` for the whole repo:

```bash
fleet_reg_state=$(BOOTSTRAP_HOOK_BASENAME="fleet-memory.sh" "$BOOTSTRAP_STATUS_SCRIPT" "$SETTINGS_REL_PATH")
if [[ "$fleet_reg_state" == "unparseable" ]]; then
    fleet_deliver=false
...
if $fleet_deliver; then FLEET_MODE=stub; else FLEET_MODE=full; fi
```

The registrar's symlink refusal is right — `open(target,"w")` follows a link and the edit lands outside the tree. The **classifier's** is not: it answers "is this hook registered?", and a symlinked settings.json that registers `fleet-memory.sh` *is* registered. Conflating "we must not rewrite this" with "the hook is not registered here" is what withdraws the stub.

Reproduced end to end on the suite's own `bootorg` bares, starting from a repo the previous sync had left perfect (`hook=current payload=current settings=registered`, AGENTS.md = the 5,687-byte stub), changing **only** `.claude/settings.json` into a symlink to a sibling committed file — a shape git stores natively (mode `120000`) and checks out as a symlink:

```
--- classifier on that file ---
  0d73ac4 : unparseable          670e1ce : registered

--- sync.sh --dry-run, repo section (0d73ac4) ---
  fleet-memory: .claude/settings.json is one we cannot parse or cannot append to — refusing to edit it, keeping the full guidance inline.
  fleet-memory: mode=full hook=missing payload=missing settings=unparseable
  skills-bootstrap: .claude/settings.json is one we cannot parse or cannot append to — refusing to edit it.
  [DRY RUN] Would update AGENTS.md (direct push to main; PR fallback if rejected)
  [DRY RUN] Would keep the FULL guidance inline in AGENTS.md (fleet-memory cannot be delivered here)

--- real run, same repo (0d73ac4) ---
  <same three lines>   Pushed directly to main.       === Sync complete: 1 synced, 5 skipped, 0 failed ===

--- the consumer, cloned fresh from the bare afterwards ---
  AGENTS.md                                5,687 -> 57,971 bytes
  .claude/hooks/fleet-memory.sh            present
  .claude/hooks/fleet-guidance.md          present
  fleet-memory REGISTERED in settings.json True
  InstructionsLoaded registered            True

--- the SAME planted repo, sync.sh from 670e1ce ---
  fleet-memory: mode=stub hook=drifted payload=current settings=registered
  AGENTS.md 5,687 -> 5,687 bytes
```

So on the first post-merge run, a consumer whose only distinguishing feature is a symlinked settings.json gains **+52 kB of AGENTS.md** while its still-registered SessionStart hook keeps writing the same 57 kB into `~/.claude/CLAUDE.md`. That is a double load of the guidance in the exact metric this whole programme exists to reduce, delivered silently with `0 failed`. It does not self-heal: nothing removes the inline block on a later run, and the `.claude/` payload and registration stay in place beside it.

Three aggravations:

- **The operator-facing reason is false for this shape.** F2 reworded the message to "is one we cannot parse or cannot append to". A symlinked settings.json parses fine and *can* be appended to — the refusal is posture, not capability. F2's own defect ("sends a reader hunting for a syntax error that is not there") is re-created by the shape added two commits later.
- **The same word also stops `skills-bootstrap` delivery** on that repo (measured, third line above), so one symlink withdraws three deliveries.
- **`hook=missing payload=missing` is wrong** in that log line (N1): both files are present in the repo; the states are simply never computed on this branch.

**The suite cannot see any of it.** The only symlink-plus-settings assertions are unit-level (`run-tests.sh:19574-19589`: the classifier says `unparseable`, the registrar refuses, the link and target are untouched). No test drives `sync.sh` against a symlinked settings.json, and the one assertion that guards this exact invariant — `assert_not_contains … "mode=full"` at `:6867` — is fixtured on the *instr* lane, which the symlink shape never reaches. 1584/0 green throughout.

**Fix.** Two options, both small:

1. Preferred — keep the classifier honest and gate the *write*: let `bootstrap-status.sh` classify a symlink by its content (`classify < "$1"`, as it does today for a regular file) and add a distinct fifth word, e.g. `readonly-registered` / `symlink`, that `sync.sh` treats as "do not edit this file" **without** flipping `fleet_deliver`. The registrar already refuses independently, so nothing can be written through the link.
2. Minimal — gate the existing branch on the fleet pair actually being absent: `if [[ "$fleet_reg_state" == "unparseable" ]] && ! fleet-memory is already registered`. This is the same shape as the `instr_deliver` split this round introduced for R2-S5: withhold the *write*, not the repo.

Either way, add a `sync.sh`-level assertion that a symlinked settings.json leaves AGENTS.md at the stub — the missing half of the R2-N7 test.

### Should-fix

**S1 — "announced exactly once" is false for two SessionStarts that begin within ~30 ms of each other: 40/40 double-announcements at zero stagger.**

`.claude/hooks/fleet-memory.sh:91-114`. `report_previous_session` greps `unread`, echoes, and only then calls `mark_receipt_read`. Two hooks in that window both see `unread=1` and both print.

```
stagger 0.000s : 20 / 20 double-announced
stagger 0.005s : 19 / 20
stagger 0.010s : 20 / 20
stagger 0.020s : 19 / 20
stagger 0.050s :  0 / 20
stagger 0.100s :  0 / 20
```

(40/40 in the first, unstaggered run of 40 pairs; no stray `.read.*` files left in any of them.)

This is not the window F5 asked to be documented. F5's comment at `:134-143` records the **lost-verdict** direction — a load-time hook writing between the grep and the sed — and calls it "microseconds wide and … not provoked". The **double-announce** direction is 20–50 ms wide, provokes 40/40, and is not mentioned anywhere. The file reasons explicitly about concurrency two paragraphs earlier (`:84-90`: "two sessions sharing one config dir erase each other's verdicts before either is announced") and covers only the erase half.

It matters because of what the PR ships. `AGENTS.md:59` and `agents-md/stub.md:54` now tell every agent on ~20 repos: *"Each of those three is announced exactly once, by the first session start that sees it."* An agent that sees the line twice has been told the receipt is broken.

**Fix:** make the read-and-clear a single claim. `mv` the receipt aside first (`mv "$RECEIPT_FILE" "$tmp"` is atomic; the loser gets nothing to read), announce from `$tmp`, then write the cleared copy back. Or accept it and say so in the shipped sentence — "announced once per session start that sees it unread" — rather than "exactly once".

**S2 — `mark_receipt_read` fails SILENTLY when the write fails rather than when `mktemp` fails: 5 of 5 consecutive session starts re-announced, no loud line, empty stderr. REPEAT of R2-N4's symptom through the brief's own remedy.**

`.claude/hooks/fleet-memory.sh:144-159`. The loud path is attached to `mktemp` alone:

```bash
if ! tmp="$(mktemp "$RECEIPT_FILE.read.XXXXXX" 2>/dev/null)"; then
    echo "fleet-guidance: could not clear the previous session's receipt — the line above will repeat next session."
    return 0
fi
{
    if sed 's/^unread=1$/unread=0/' "$RECEIPT_FILE" > "$tmp"; then
        mv "$tmp" "$RECEIPT_FILE"
    fi
    rm -f "$tmp"
} 2>/dev/null
```

On a full filesystem `mktemp` succeeds (a zero-byte file fits) and the `sed > "$tmp"` fails with ENOSPC. That failure is caught by the `if`, discarded by `2>/dev/null`, and the function returns 0. Measured on a 256 KiB tmpfs filled to 0 K free, config dir and receipt both on it:

```
  SS#1 announced=1  'could not clear' line=0  unread=1
  SS#2 announced=1  'could not clear' line=0  unread=1
  SS#3 announced=1  'could not clear' line=0  unread=1
  SS#4 announced=1  'could not clear' line=0  unread=1
  SS#5 announced=1  'could not clear' line=0  unread=1
  (space restored)  SS#6 announced=1, unread=0 — converges only once the disk is free
```

Every stderr empty. The control is the *other* failure mode: with the config dir `chattr +i`, `mktemp` genuinely fails and the loud line **does** fire, 1 per session start, 3/3 — so the mechanism works, it is just wired to the rarer half.

The comment at `:121-128` states the wider claim: *"when it cannot create a file at all this says so out loud rather than looping in silence — the one thing a 'never silent for more than one session' contract cannot afford is a silent failure to clear."* A write that fails is a silent failure to clear, and the brief's own R2-S3 item asked for exactly this: *"write the cleared receipt through a `mktemp`-named tmp beside it (**or fail loudly in the verdict line**)"*.

**Fix:** move the loud line to cover the whole compound — capture the result of the `sed`/`mv` pair and print the same sentence when it did not happen. Three lines, and the same test that pins the `mktemp` failure can be re-run with the write failing.

**S3 — a directory named `.claude/settings.json` in one consumer aborts the ENTIRE fleet sync run: exit 2 after 1 of 6 repos, no summary, no failure tally. The class F6's remedy claims, through the argument rather than the environment.**

`scripts/bootstrap-status.sh:154-157` exits 2 for a directory. `scripts/sync.sh:849-850` and `:870-872` call it in a command substitution under `set -euo pipefail`, so that exit is the run's exit.

`.claude/settings.json` as a **directory** is representable in git (a tree with any file under it) and checks out normally. Planted on `bootorg/repo-adopted`, which sorts first of six:

```
=== bootorg/repo-adopted ===
  Sections: python
bootstrap-status.sh: .claude/settings.json is a directory; pass its .claude/settings.json
<end of output>            rc=2      repos reached: 1 of 6      no "Sync complete" line
```

Identical on `670e1ce` (rc 2, 1 of 6) and the guard is present on `main`, so this is **pre-existing, not a regression**. It is graded here because F6 named this precise failure shape — *"`bootstrap-status.sh` ~:59-62 exits 2; `sync.sh` calls it in a command substitution under `set -euo pipefail` … measured exit 2 after 1 of 6 repos, no summary"* — and closed it only for ambient `BOOTSTRAP_HOOK_*` values, which are an operator's own environment. The door that a *consumer repo* can open, on a public repo the fleet syncs unattended, is still there. The whole point of the gitignore handling at `sync.sh` (and the assertion at `run-tests.sh:6453-6455` that the run *survives* a gitignored `.claude/`) is that one repo's shape must fail one repo.

**Fix:** either classify a directory as `unparseable` (it is, in the sense every caller means) instead of exiting 2, or wrap both call sites: `fleet_reg_state=$("$BOOTSTRAP_STATUS_SCRIPT" "$SETTINGS_REL_PATH") || fleet_reg_state=unparseable`. Test: the fixture repo carrying a directory there is skipped with a WARN and the other five are still processed.

**S4 — a consumer whose `.claude` is a SYMLINK kills the fleet run at `git add`: `fatal: … is beyond a symbolic link`, exit 128, 1 of 6 repos, no summary.**

`scripts/sync.sh:1336`, `git add "${add_paths[@]}"`, unguarded under `set -euo pipefail`. A repo that stores `.claude -> config` (a shape git stores natively and a plausible monorepo/dotfiles convention) passes every check — the classifier reads the settings fine through the link and answers `registered` — and then dies when the sync has to stage a file under it:

```
=== bootorg/repo-adopted ===
  fleet-memory: mode=stub hook=current payload=current settings=registered
  instructions-loaded: hook=missing settings=no-entry
  instructions-loaded: hook missing — written.
  instructions-loaded: settings.json — registered.
fatal: pathspec '.claude/hooks/instructions-loaded.sh' is beyond a symbolic link
                            rc=128     repos reached: 1 of 6     no summary
```

Pre-existing: `670e1ce` dies the same way on the same repo (`fatal: pathspec '.claude/hooks/fleet-memory.sh' is beyond a symbolic link`, rc 128, 1 of 6). What this PR adds is a **third** path into `add_paths` (`sync.sh:1325`, `$INSTR_HOOK_REL_PATH`), i.e. one more way for an already-delivered repo to newly need a staged file under that link.

Note the ordering hazard: the registration was already written into the clone before the abort. The clone is thrown away, so nothing reaches the consumer — but the run reports nothing at all about the five repos it never touched.

**Fix:** the same guard as S3 — `git add … || { fail "$repo_name: could not stage …"; ((FAIL_COUNT++)); cd "$REPO_ROOT"; continue; }` — so one repo's shape fails one repo and the tally says so.

### Nit

**N1** `sync.sh:894` prints `hook=missing payload=missing` on the `fleet_reg_state == unparseable` branch even when both files are present in the repo: the states are initialised at `:835-836` and only computed inside the `else` at `:855-866`. Measured on the B1 repo, where `.claude/hooks/fleet-memory.sh` and `fleet-guidance.md` are both committed and present. The line is the operator's only view of that repo.

**N2** A **FIFO** at `.claude/settings.json` hangs `register-bootstrap-hook.sh` forever at `:199` (`open(target, "w")` blocks for a reader) and **leaks a blocked `python3` child** that survives the wrapper — R2-S2's exact shape, on the registrar, uncovered by the R2-S1/S2 remedy (which touched only the hook). Measured: rc 124 at my 20 s bound, one `python3 -c 'import copy, json, os, sys…'` still alive afterwards (killed). Not reachable through `sync.sh` (git cannot store a FIFO, and the classifier answers `missing` for one before the registrar is called), which is why it is a nit. `os.O_NONBLOCK` or an `S_ISREG` check would close it the same way the hook's did.

**N3** The registrar on a **directory** target dies with a raw traceback (`IsADirectoryError: [Errno 21]`) and exit 1, printing nothing on stdout — so `sync.sh:1314` would log `WARN: could not register … () — leaving it untouched` with an empty reason, the exact shape the file's own comment at `:93-96` says it fixed for `BOOTSTRAP_HOOK_TIMEOUT=abc`.
