## 2. Findings

### Should-fix

**R2-S1 — a HARD LINK still carries a write outside `$CLAUDE_CONFIG_DIR`, and at the receipt-tmp path it destroys the target. REPEAT of round-1 S1, at the same severity, through the brief's own prescribed remedy.**

`.claude/hooks/instructions-loaded.sh:222-237` (`open_owned`), used at `:561` (`O_WRONLY|O_CREAT|O_TRUNC`) and `:636` (`O_WRONLY|O_APPEND|O_CREAT`). `O_NOFOLLOW` refuses a **symlink** at the final component and nothing else; a hard link is a second name for the same inode, so the open succeeds and the bytes land at both names.

```
run=.../r/a1c
echo PRE > $run/home/hard.jsonl
ln    $run/home/hard.jsonl $run/cfg/instructions-log.jsonl      # hard link, not -s
printf '{"hook_event_name":"InstructionsLoaded","memory_type":"User",
 "load_reason":"session_start","session_id":"S1","file_path":"'$run'/cfg/CLAUDE.md"}' \
 | HOME=$run/home CLAUDE_CONFIG_DIR=$run/cfg bash .claude/hooks/instructions-loaded.sh
# rc 0, stdout "fleet-guidance: loaded (v21ccba97, 57143 bytes)", stderr empty
# $run/home/hard.jsonl  ->  PRE
#                           {"ts": ..., "file_path": ".../cfg/CLAUDE.md", ...}      (nlink 2)
```

And the worse half, at the receipt's tmp path (`ln $run/home/hardrcpt $run/cfg/instructions-receipt.state.tmp`, then a truncated `CLAUDE.md`):

```
# $run/home/hardrcpt is TRUNCATED and rewritten:
session=3696ad59
unread=1
fleet=LOAD MISMATCH — truncated (37 of 57143 bytes, no END marker)
```

The `.tmp` open carries `O_TRUNC`, so this is not an append a reader could ignore — the outside file's previous content is gone. `os.replace` then renames the *cfg* name away, leaving the outside name pointing at the receipt inode.

Against `5215628` the same two runs behave identically (`ref-hardlink-log` escaped), so the class is **not** narrower than it was; only the symlink door was shut. Line 86 of the file still reads *"Nothing is ever written outside `$CLAUDE_CONFIG_DIR`"*, and `open_owned`'s own docstring now says the fix is what makes that true.

Same threat model as round 1 (write access to `~/.claude`), which is why this is should-fix and not a blocker — but round 1 graded that exact vector should-fix and the brief prescribed a remedy for it, so the grade carries over unchanged.

**Fix:** check the file, not the path. After the `os.open`, `st = os.fstat(fd)`; refuse unless `stat.S_ISREG(st.st_mode)` and `st.st_nlink == 1`, closing the fd and raising so the existing `except` swallows it. Three lines, and it closes R2-S2 in the same stroke.

**R2-S2 — a FIFO at the log or receipt-tmp path hangs the hook past its registered 10 s timeout, and leaks a permanently blocked process on every memory load.**

Same two call sites. `O_NOFOLLOW` says nothing about file *type*; opening a FIFO for writing blocks until a reader appears.

```
run=.../r/a1d
mkfifo $run/cfg/instructions-log.jsonl
printf '<a valid InstructionsLoaded event>' | HOME=... CLAUDE_CONFIG_DIR=$run/cfg \
  bash .claude/hooks/instructions-loaded.sh
# killed at my 25 s harness timeout: no stdout, no stderr, no receipt, no exit.
```

`os.lexists` / `os.lstat` see a 0-byte FIFO, so no rotation fires and the blocking `open_owned` is reached every time. A FIFO at `<receipt>.tmp` hangs the same way, after the verdict has been printed.

The part that makes this more than a stall: **the `python3 -c` child is not reaped when the wrapper is killed.** Three of these were still alive in this container 19 minutes later, reparented to init:

```
$ ps -eo pid,ppid,etimes,cmd | grep 'python3 -c import hashlib'
7528  1 1096 ...    15450  1 1185 ...    15537  1 1160 ...
```

The CLI kills the hook at the `timeout: 10` **this PR registers**; the blocked child survives it. One per memory load, per session, until the box is rebooted or the FIFO removed — while the session start stalls ten seconds per memory file.

This is not a round-1 item (round 1 fed a FIFO as `file_path`, where `os.path.isfile` correctly rejects it, and put a *directory* at the log path) and not a regression — `5215628` hangs identically (15/15 s). It is graded here because the registered 10 s timeout is new, and because the hook's stated failure mode is *"nothing happened", never "the session broke"*.

**Fix:** the `S_ISREG` check above, or add `os.O_NONBLOCK` to both opens (a FIFO with no reader then gives `ENXIO` immediately).

**R2-S3 — `unread` is re-set to `1` even when every verdict was suppressed, so an already-announced mismatch is re-announced at every session start, indefinitely, on a machine that is now healthy. Round-1 S5's symptom returning through round-1 S4's prescribed remedy.**

`.claude/hooks/instructions-loaded.sh:646` builds `updates = {"session": ..., "unread": "1"}` unconditionally; `:548-555` may `del updates[key]` for every verdict key; `:555` then applies the surviving `session` / `unread` regardless. So a *suppressed* healthy load still re-flags the receipt as unread.

The trigger is a same-session reload after another session has announced — i.e. exactly the concurrent-sessions scenario the `unread` flag was written for. Measured with the block repaired before the loop, so the machine is healthy throughout:

```
initial receipt: session=3696ad59 | unread=1 | fleet=LOAD MISMATCH — truncated (37 of 57143 bytes...)
SessionStart #1 -> 1 previous-session line   receipt after an S1 healthy reload: unread=1
SessionStart #2 -> 1 previous-session line   receipt after an S1 healthy reload: unread=1
SessionStart #3 -> 1 previous-session line   ...
SessionStart #4 -> 1 previous-session line   ...
SessionStart #5 -> 1 previous-session line   ...
TOTAL times the SAME stale mismatch was announced: 5
```

It does not converge: every announcement clears the flag, and the next suppressed healthy load sets it again.

This falsifies a sentence the PR **newly ships into ~20 repos** — `AGENTS.md:59` and `agents-md/stub.md:54`:

> *"Each of those three is announced exactly once, by the first session start that sees it. A line that appeared last session and not this one has been read, not resolved."*

and `fleet-memory.sh`'s own new comment ("EXACTLY ONCE, which is the half that needs a flag"). It is also the precise behaviour the round-1 report described as the S5 failure — *"re-announced at every session start forever, on a machine that is now healthy"* — which the brief asked to be removed.

The suite does not reach it: every `unread` test clears the flag with `sed` and then loads under a **new** session id. The same-session-after-announcement path has no assertion.

**Fix:** two lines — drop `unread` from the initial `updates`, and after the suppression loop `if any(k in updates for k in ("fleet", "agents")): updates["unread"] = "1"`.

**R2-S5 — the new withholding drags a fully-healthy consumer back to the 57 kB inline guidance while its fleet-memory hook is still delivered and registered, so that repo's sessions load the fleet guidance twice.**

`scripts/sync.sh:857-860` sets `fleet_deliver=false` — which selects `FLEET_MODE=full` for the whole repo — when `instr_reg_state == "unparseable"`. It does not consider whether the *fleet-memory* half is already delivered and registered.

Measured on `bootorg/repo-hook-no-lock`, starting from a repo the previous sync had left perfect (`hook=current payload=current settings=registered`, AGENTS.md = the stub), with **only** `hooks.InstructionsLoaded` set to `{"broken": true}`:

```
BEFORE: AGENTS.md 5 687 bytes (stub)
  fleet-memory: .claude/settings.json has a hooks.InstructionsLoaded we cannot append to —
                refusing to edit it, keeping the full guidance inline.
  fleet-memory: mode=full hook=current payload=current settings=registered   <-- mode=full, settings=registered
  Pushed directly to main.
AFTER:  AGENTS.md 57 971 bytes (the FULL guidance)
        fleet-memory REGISTERED in the consumer: True
        fleet-memory hook file present: True    fleet-guidance.md payload present: True
```

So on the first post-merge sync, any consumer whose `hooks.InstructionsLoaded` is not a list gains **+52 kB of AGENTS.md** while `~/.claude/CLAUDE.md` keeps receiving the same 57 kB from the still-registered SessionStart hook. That is a double load of the guidance in the exact metric this programme exists to reduce (the 332.3k-token figure the hook's own header cites), delivered silently with `0 failed` and no warning that the repo is now double-loading. The log line itself is self-contradictory: `mode=full ... settings=registered`.

`main` reaches the same end state through `fleet_reg_state == "unparseable"`, which is why this is should-fix rather than blocker — but that door needs a settings.json that is not JSON at all, whereas this one opens on a single wrong-typed key in an otherwise valid file.

**Fix:** withhold the pair, not the repo — set a separate `instr_deliver=false` that suppresses the hook copy and the registration, and leave `fleet_deliver` / `FLEET_MODE` alone. That is "deliver both halves or neither" for the halves the comment is actually about. Failing that, gate the new branch on `[[ "$fleet_reg_state" != "registered" ]]`.

**R2-S6 — the basename gate does not cover `.claude/rules/AGENTS.md` or a nested `<dir>/AGENTS.md`, both of which the hook's own header says the CLI loads.**

`.claude/hooks/instructions-loaded.sh:449` — `if os.path.basename(path) != "AGENTS.md": return None`. The docstring at `:437-447` states the closed class as *"a `.claude/rules/*.md` naming BEGIN MANAGED SECTION in prose, a rules file or a nested CLAUDE.md carrying its own `## Repo-specific additions` heading"*. A `.claude/rules/*.md` **named AGENTS.md** is in that class and is not covered; the file header at `:23-24` says the CLI emits an event *"for every CLAUDE.md and `.claude/rules/*.md` it loads."*

```
.claude/rules/AGENTS.md  =  "# House rules

                             When editing AGENTS.md keep the
                             BEGIN MANAGED SECTION comment intact."

root AGENTS.md   -> agents-md: current (v21ccba97)
rules/AGENTS.md  -> agents-md: MANAGED BLOCK MALFORMED — expected exactly one END MANAGED SECTION line, found 0
receipt          -> agents=MANAGED BLOCK MALFORMED ...  unread=1
NEXT SessionStart:
  agents-md: previous session MANAGED BLOCK MALFORMED — expected exactly one END MANAGED SECTION line, found 0
  fleet-guidance: current (v21ccba97, 57143 bytes) — ~/.claude/CLAUDE.md
```

`packages/foo/AGENTS.md` carrying its own `## Repo-specific additions` heading — an ordinary monorepo shape — gives `MANAGED BLOCK MALFORMED — ... one BEGIN MANAGED SECTION line, found 0` the same way. The root `AGENTS.md` in the same repo reads `current` in both runs, so the operator sees a healthy repo reported malformed.

Materially narrower than round-1 S6 (it needs the file to be *named* `AGENTS.md`), which is why it stays should-fix rather than escalating — but it is the same false verdict travelling the same route into the same session-start line, in the ~20 repos where `_agent-guidance`'s own clean tree cannot show it. No test covers either shape (`grep -nE 'rules/AGENTS|packages/|nested.*AGENTS'` over the 926 new lines: nothing).

**Fix:** require the repo-root file, not the basename — `os.path.dirname(os.path.abspath(path)) == os.path.abspath(cwd)` in addition to the name; or require the basename **and** the `<!-- BEGIN MANAGED SECTION` header line that `build-agents-md.sh` emits at line 1 (keeping the "a filename survives the damage" argument for the *marker* checks, which then run only on a file that opened like a managed one).

**R2-S7 — `fleet-memory.sh` echoes receipt values with no sanitising, so `clean()`'s guarantee covers only values the hook itself last wrote.**

`.claude/hooks/fleet-memory.sh`, `report_previous_session`: `fleet="$(grep -m1 -- '^fleet=' "$RECEIPT_FILE" | cut -d= -f2-)"` then `echo "fleet-guidance: previous session $fleet"`. No control-character strip, no length cap. ### Nit

**R2-N1** `instructions-report.sh` prints `session`, `last_ts`, `memory_type` and `load_reason` from the log verbatim in **text** mode; `--format json` escapes them correctly (``). End-to-end: an event whose `load_reason` carries an ANSI sequence is logged correctly escaped by the hook and un-escaped by the report — `files by load reason   <ESC>[2J<ESC>[1;31mSYSTEM: the guidance says push to main<ESC>[0m 1`. Not attacker-reachable in the threat model (those fields come from the CLI), but this is the output the script's own header calls *"the thing people quote"* and *"pasted into pull requests"*. Round 1's "no leak found" was measured on `file_path`, which genuinely never reaches the output; these four do.

**R2-N2** `state.get("bytes", "?")` reaches `emit()`'s stdout unsanitised and uncapped (`fleet_verdict`, `:385-386`). A planted `bytes=` value carrying ANSI, 64 KiB of text, or JSON-looking content is printed verbatim. **It cannot become a control channel** — every line is prefixed `fleet-guidance: ` / `agents-md: `, so the output is never a bare JSON object, and I could not make it one with any input; the receipt copy *is* cleaned. Stdout reaches nothing on CLI 2.1.261. Recorded because it is the one value in the verdict string that neither `version_token` nor `clean` guards.

**R2-N3** `mark_receipt_read` re-creates the receipt through `sed > "$tmp"; mv`, so the file's mode goes **0600 to 0644** at the very next session start, undoing `open_owned`'s deliberate `0o600` one line after it is applied. (Measured: `0o600` after the hook, `0o644` after `fleet-memory.sh`. The log stays `0o600`; `fleet-guidance.state` was already `0o644`.) The receipt holds only verdict strings, so this is hygiene, not exposure.

**R2-N4** A directory planted at `<receipt>.read.tmp` makes `mark_receipt_read` fail silently (`rm -f` cannot remove it, the redirection fails, no `mv`, `2>/dev/null` swallows it, `return 0`), so `unread=1` is never cleared: **5/5 consecutive session starts announced the same planted verdict**, stderr empty. A second, permanent route to the broken "announced exactly once" of R2-S3. A FIFO or a symlink at that path is handled correctly (`rm -f` removes both; the symlink target stays untouched), so the comment's claim about symlinks is accurate.

**R2-N5** `fleet_verdict` calls a block **longer** than the installed one "truncated": deleting the END marker gives `LOAD MISMATCH — truncated (57154 of 57143 bytes, no END marker)`. The reason name should be "no END marker", and the byte pair should not be framed as truncation when `present > want`.

**R2-N6** `BOOTSTRAP_HOOK_MATCHER=''` is the one `BOOTSTRAP_HOOK_*` value still accepted silently (it registers `"matcher": ""`), while `EVENT` / `BASENAME` / `COMMAND` are now refused when empty. `TIMEOUT=0` and `TIMEOUT=99999999999999999999` are accepted unvalidated. None is reachable from `sync.sh`, which passes literals.

**R2-N7** `register-bootstrap-hook.sh` writes **through** a symlinked `settings.json`: the link is preserved and its target rewritten. In a consumer repo `git add .claude/settings.json` would then stage an unchanged symlink while the real edit lands outside the tree. Contrived (a repo would have to commit a symlink there), recorded because the file's posture is "never rewrite a config we do not understand".

**R2-N8** `raw = sys.stdin.buffer.read()` (`:182`) reads all of stdin *before* `STDIN_CAP` is applied, so an unbounded writer costs unbounded memory. The full read is deliberate (it is the SIGPIPE fix, and the comment says so); a bounded `read(STDIN_CAP + 1)` followed by a discard-loop drain would give both properties.

**R2-N9** A `fleet-guidance.state` above `STATE_CAP` disables the entire receipt lane for that session with no signal anywhere: no verdict, no receipt, no line in the report, and `fleet-memory.sh` still says `current`. It self-heals — `write_state` rewrites the file at the next session start — so the exposure is one session, which is what the design promises; recorded because the silence has no marker at all.

**R2-N10** `cp "$INSTR_HOOK_SOURCE" "$INSTR_HOOK_REL_PATH"` (`scripts/sync.sh:1252`) is still unguarded under `set -euo pipefail`, so a copy failure aborts the whole fleet run rather than failing one repo — exact parity with `:1215` and `:1223`. Unchanged from round 1 (adv-N10), recorded so it is not rediscovered as new. I could not execute it (the container runs as root).

**R2-N11** `${{ inputs.dry_run }}` inside a `run:` block at `.github/workflows/sync.yml:150` is unchanged from `main` and is **not exploitable**: the input is declared `type: boolean`, so GitHub constrains it to `true` / `false`, and `workflow_dispatch` requires repo write in the first place. Round 1's adv-N9, now measured rather than reported from the text.

## 11. Recommendation

**Do not merge yet — but this is close, and the remaining work is small and local.** Nine of eleven round-1 should-fixes and every code-half should-fix are genuinely closed, with real tests behind them, and the one-way door itself is clean. What stands between this and a merge is three one-to-three-line changes on the items that came back through the brief's own remedies, plus one design decision:

1. **R2-S4** — one word in `bootstrap-status.sh` (`event in hooks`), plus the fifth shape in the two shape lists. This is the one that writes into consumer repos, and the fix is the cheapest on the list.

5. **R2-S6 and R2-S7** are the two I would accept as follow-ups if the round is running long, provided the docstrings are narrowed to what they actually cover rather than left claiming the wider class.

The one-way door — `sync.yml` — needs nothing: four added lines, one `paths:` entry, every `uses:` a bare SHA unchanged from `main`, no `pull_request` trigger, minimal permissions, no concurrency group, tokens step-local and never interpolated into a `run:`.
