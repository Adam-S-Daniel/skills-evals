### B1 (should-fix, same-class repeat of N6) — inverted single-job wiring scores 12/12

`evals/post-failure-comment/fixture.yaml:111` (`if_contains: "failure()"`) and `:132` (`if_contains: "success()"`) decide the polarity of the `e2e-post-step` / `e2e-resolve-step` gates with a substring test. A negation contains the token:

```
e2e post   if: ${{ !failure() && github.event_name == 'pull_request' }}   mode: post
e2e resolve if: ${{ !success() && github.event_name == 'pull_request' }}  mode: resolve
```

This posts the failure comment on every green run and resolves it on every red one — the exact wrong answer N6 was raised to catch — and scores **12/12, zero failing checks** (workspace 17). The plain swap (post on `success()`, resolve on `failure()`) correctly scores 10/12 (workspace 18), which is what makes the gap easy to miss: the obvious inversion is caught, the negated one is not.

`_gates_on_outcome` already handles this correctly — measured directly:

```
_gates_on_outcome('!failure()', 'failure') = False     _gates_on_outcome('!failure()', 'success') = True
_gates_on_outcome('!success()', 'success') = False     _gates_on_outcome('!success()', 'failure') = True
```

Fix is two lines: `if_gates_on_outcome: failure` on `e2e-post-step` and `if_gates_on_outcome: success` on `e2e-resolve-step`, alongside the existing `if_contains`. Verified at head — skill-faithful workspace stays **12/12**, the negated inversion drops to **10/12**.
