## Findings

### Blockers

**B1 — The answer key ships inside the agent's workspace.**
`evals/rename-pdfs/seed/expected.txt:1-6` and `evals/rename-pdfs/seed/make_pdfs.py`,
copied verbatim into the agent's cwd by `harness/run_eval.py:517` in **both** arms.
*Reproduce:* `python3 -c "import shutil; shutil.copytree('evals/rename-pdfs/seed','/tmp/ws')"; ls /tmp/ws`
→ `expected.txt`, `inbox/`, `make_pdfs.py`. Then map the four scanner names onto the four
names in `expected.txt` and score: **2/2, exit 0, without opening a single PDF**
(measured above). `make_pdfs.py:104-105/85-87/177` separately states all three of the
"non-obvious things" the fixture's own header claims to be measuring.
*Fix:* move the expected listing into `fixture.yaml` as an inline `expected:` list (the
check type already supports and tests it — **no harness change needed**) and move
`make_pdfs.py` to `evals/rename-pdfs/make_pdfs.py` with its `--out-dir` default retargeted
at `seed/inbox`. `seed/` then holds only `inbox/`. Alternative (b) in decision 1 keeps a
separate file by resolving `expected_file` against the fixture directory; I would take the
inline list.

**B2 — The decisive check fails the behaviour the skill prescribes.**
`evals/rename-pdfs/fixture.yaml:59-68` lists `inbox/` whole, and SKILL.md:123 step 6
requires the rename log be written **"in the same folder"** — SKILL.md:83/93 confirm the
log is expected to sit among the PDFs.
*Reproduce:* build the correct renames, `touch "inbox/pdf-rename-log-2026-09-05.csv"`,
score → `FAIL … unexpected: pdf-rename-log-2026-09-05.csv`, exit 1. Same workspace with
the log outside `inbox/` → exit 0.
This penalizes the `with_skill` arm for following the skill, in the fixture's only
correctness check, and the log's name is wall-clock-derived (against DESIGN.md:243's "no
wall-clock"), so it cannot simply be added to the expected list.
*Fix:* give `dir_listing_matches` an optional `ignore:` list of fnmatch globs compared as
data (`fnmatch.fnmatch`, not regex), and set
`ignore: ["pdf-rename-log-*.csv"]` on this check with a comment saying why — the skill
mandates that artifact and its name carries the run date. Do **not** narrow the listing to
`*.pdf`: that would let an agent hide a `.bak` or a subdirectory and still pass, which the
current whole-listing comparison correctly catches (measured: `unexpected: archive`,
`unexpected: .hidden`). Add a test for the ignore path and a mutation test that the ignore
glob is not silently swallowing real extras.

### Should-fix

**S1 — The skill's own helper cannot parse the statement's date, and points at the wrong answer.**
`evals/rename-pdfs/seed/make_pdfs.py:114` (`Billing Period: 1 Jan 2026 to 31 Jan 2026`).
*Reproduce:* `find_dates()` from the skill's `extract_pdf_context.py` returns `[]` for the
statement's text and `['2026-02-05']` for its filename — none of its four `DATE_PATTERNS`
matches a day-first bare-month form, and its own 12-test suite has no such case. An agent
following the skill's documented priority on the helper's parsed output lands on
`20260205-Statement-…` and fails the listing check (measured). The issue prescribed that
literal string, so this is not a worker error — but it makes the `with_skill` arm's tool
a liability on 1 of 6 files, in a check with no partial credit.
*Fix:* either write the period as `January 1, 2026 to January 31, 2026` (parses to both
endpoints, still a range, still the same test), or keep the string and add a fixture
comment recording that the helper cannot parse it deliberately — and if deliberate, say so
in the PR, because it changes what the fixture measures.

**S2 — The per-file-confirmation rule vs. a headless single-shot run.**
SKILL.md:151: *"**Never batch-rename without per-file confirmation** unless the user
explicitly types `auto` mid-session"*, and the whole of Workflow step 4 is an interactive
loop. `run_agent` (`harness/run_eval.py:404`) invokes `claude -p <prompt>` — one shot, no
user, nobody to answer. A maximally faithful `with_skill` agent proposes six names, asks,
and renames nothing; the `without_skill` agent has no such instruction and just renames.
This is a second mechanism biasing the same direction as B2. I could not measure it (no
real run is possible here), which is exactly why it should be decided deliberately rather
than discovered in the N=3 numbers.
*Fix:* either add a line to the prompt granting autonomy (`… Go ahead and apply them
without checking with me.`) — which changes the issue's prescribed prompt and should be
called out — or record the confound in the fixture header and in the PR so the first real
run is read with it in mind. Do not leave it unstated.

**S3 — The two pypdf-gated tests never run in any environment this project uses.**
`test/run_tests.py:2780-2793`. `.github/workflows/ci.yml:88` installs `pyyaml` only, so
they skip in CI as they skip here. They are the only assertions guarding the fixture's two
core premises.
*Reproduce:* changing `Invoice Date: February 14, 2026` → `March 1, 2026` in
`seed/make_pdfs.py` — which deletes the decoy the whole `date_priority` dimension rests
on — leaves the suite at **187 tests, OK** (measured).
*Fix:* keep the pypdf tests, and add byte-level equivalents that always run: assert the
image-only PDF contains no `Tj`/`TJ`/`BT` operator and no `/Font`, and assert the
invoice's content stream contains `February 14, 2026` and not `20260301`. Both are three
lines against uncompressed streams, hermetic, and would have caught the mutation above.
While there, add the missing generator-drift test — regenerate to a temp dir and assert
byte equality with the committed PDFs (it holds today; nothing checks it).

**S4 — A non-UTF-8 `expected_file` raises out of `run_checks` and kills the run.**
`harness/scorers/objective.py:465-468` — `open(..., encoding="utf-8")` guarded by
`except OSError` only.
*Reproduce:* `objective.dir_listing_matches(ws, ["inbox"], expected_file="bad.txt", seed=seed)`
with `bad.txt` containing `b"a.pdf\n\xff\xfe"` → `UnicodeDecodeError` propagates.
`_run_arm`'s only handler is a `finally:`, so this takes down the whole arm — and with
`--arm both`, the other arm too — with a bare traceback and no `report.md`/`summary.json`.
That is precisely the failure class `run_eval.py:539-556`'s `registry_error` block exists
to prevent.
*Fix:* `except (OSError, UnicodeDecodeError) as exc:` — one word.

**S5 — README and DESIGN not updated for the new fixture.**
`README.md:31-43` (Layout tree lists the other four eval dirs, not `rename-pdfs`;
precedent `f335a44` added `windows-elevation-from-wsl` to that tree in the same commit as
the eval) and `DESIGN.md:184` (still lists `rename-pdfs` as a Class A *candidate*).
*Fix:* add the `rename-pdfs/` entry to the README tree, and in DESIGN.md either strike it
from the candidate list or mark it covered the way `windows-elevation-from-wsl` is at
`DESIGN.md:282`.

**S6 — The check pair cannot bind content to a name.**
`fixture.yaml:59-81`. `dir_listing_matches` is a bag of names, `files_unchanged
by: digest` is a bag of digests; nothing pairs them.
*Reproduce:* rename the statement to the invoice's expected name and vice versa, and swap
the two bills: **both checks PASS, exit 0** (measured). The test class already encodes the
true mapping in `TestIssue82.ORIGINAL_TO_CORRECT` — no check consumes it.
*Fix:* add a third check pairing each expected name with its expected sha256 (e.g. a
`file_digests_match` taking a `{name: sha256}` mapping, or an expected file of
`<sha256>  <name>` lines), which also closes the "content preserved" check's blind spot
without weakening the bag semantics that catch the clobbered duplicate. Related: consider
splitting the one all-or-nothing listing check into per-behaviour checks (image-only name
present, pre-named file present, both bill names present, statement uses the range form)
— DESIGN.md:237 says "3–8 small fixtures per skill beat one big one", and today a run
that gets 5 of 6 names right scores identically to one that renamed nothing.

### Nits

- **N1** — `fixture.yaml:80` `paths: ["inbox/*.pdf"]`: a rename that lands outside the glob (e.g. the literal `…9002.pdf (2)` reading of SKILL.md:121) reports `1 file(s)' content missing from the result` when nothing was lost. - **N3** — `dir_listing_matches` does not validate `patterns[0]` as a workspace-relative path; `[".."]` happily lists the parent and dumps every entry into an uncapped `detail` string (measured: ~250 entries).
