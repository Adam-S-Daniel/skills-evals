## NIT — N8's fix publishes a non-UTC census timestamp as if it were UTC: a wrong time on `latest.json`, `summary.md` and stdout, where the raw string used to be right

`harness/roster.py:1041`:


The age check keeps using the correct aware value, so the published provenance now

## NIT — `_format_share`'s `:.6g` fallback re-prints the bar, so "below the 2% exit bar (2% of rankable census usage)" is still reachable

`harness/roster.py:375-379`:


## NIT — the 500-entry cap evicts by ID SORT, not by age, and `roster-policy.yml` says otherwise; an attacker picks which real history dies

`harness/roster.py:775-776` keeps the alphabetically-first non-live entries.
`evals/roster-policy.yml:137-139` describes the same cap as
"(currently 500 entries, oldest-by-id-sorted-out first among non-live entries…)", which
reads as an age order the code does not implement. Measured
(`$SP/rev129g-atk/a12_cap_evict.py`, 20 real since-retired ids + 500 plants):

```
500 plants sorting AFTER the real history   -> real history kept 20/20, plants kept 477
500 plants sorting BEFORE it ("0plant-…")   -> real history kept  0/20, plants kept 497
… and with the real history dated 179 days ago and every plant dated today, the OLDER
  real entries are still the ones dropped: real history kept 0/20
```

`PREVIOUS_ARM_ID_RE` allows a leading digit, so `0plant-0000` sorts ahead of every
`claude-…` id. Capability-wise this is bounded — anyone who can write `previous.json` can
delete the same entries outright — which is why it is a nit, not a should-fix. What it
costs is the property the cap was added to protect: the surviving 500 are the ones with
the smallest ids, not the ones most recently seen, and the warning is count-only, so a
silent, permanent loss of real history looks identical to normal truncation. Sorting the
non-live entries by `last_seen` (newest first) before the cap is the same two lines.
