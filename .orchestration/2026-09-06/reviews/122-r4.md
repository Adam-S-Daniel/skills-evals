### (a) Which fallback strategy, and is it symmetric?

The worker chose **the nearest-heading strategy** (the brief's second option): `loadManifestWithFallback` (`:436-487`) tries **exact** file+text first, reserving each exactly-matched heading in a `claimed` set, then resolves each remaining tip row to the Levenshtein-nearest **unclaimed** heading in its own file and rewrites `row.heading` to that text. `levenshtein`/`nearestHeading` are copied from `check-guidance-coverage.js:161-188` (deliberately duplicated, comment at `:356-362`).

This was the **only** option that could satisfy the brief's own acceptance test. Option 1 ("treat unresolvable-at-head as not checkable, skip") makes fixture (a1) exit **0**, contradicting the brief's requirement that it "exits 1 naming `edit`". So the choice is defensible.

It **is** applied symmetrically in the sense that matters: the same function, with the same base-tip row set, is used for head (`:997`, `required: true`) and for the merge-base (`:998`, `required: false`), and it only *fires* at a sha where the manifest file is genuinely absent. Both sides of the pre-manifest fork therefore go through the identical code path.

What it is **not** is *stable*: the approximate pass is greedy and order-dependent (`:473-486`, first-come reservation over `tipById`'s insertion order), unbounded (no edit-distance cap), and blind to body similarity. See the blocker in §5.

### (b) Which S2 rule, and can it be defeated?

**"Every added entry must differ from every base entry"** — `dedupedAdded` (`:635-642`) filters `addedEntries`' output by full `entryIdentity` (heading + full body) against a `Set` of *all* base identities, not just the occurrence the count-diff matched.

Defeats measured: a copy with **one character** changed in Motivation (b2) passes; a copy with **only the date bumped** (b3) passes. The brief's alternative rule (added entries dated no earlier than the merge-base commit) would have caught b2 but not b3 — and would have rejected b4, a legitimate shape the suite's own fixtures depend on. Neither rule is complete; the chosen one is the one that does not break the fixtures. Worth stating in the docs rather than fixing.

### (d) Newest-first

`d2` (correct entries, documented order violated) exits **0**. The newest-first rule is **not** enforced anywhere — there is no separate named check, and `appendOnlyViolation`'s comment (`:666-670`) says so explicitly. `docs/guidance-impact.md:15` still states "Entries append in the same PR as the change, newest first," and the surviving message at `:680` still says entries are "never removed or **reordered**", which is now inaccurate. ## 5. Findings

### BLOCKER

**F1 — B1's nearest-heading fallback still manufactures a false `remove`, and now also fails open.** `scripts/check-guidance-touch.js:473-486` (the approximate pass) + `:779` (`computeTouched`'s remove branch).

The approximate pass is a **greedy, uncapped, order-dependent** assignment: rows are walked in `tipById` insertion order and each takes the nearest *still-unclaimed* heading in its file. With one unresolved row it is correct (that is fixture #43). With two, it crosses them, and with a competing heading nearer than the true rename target it picks the wrong one. Three measured shapes, all on the pre-manifest-fork path the fallback exists for:

1. **The round-3 harm reproduces.** `$SP/hist122/b1_greedy` — a pre-manifest fork where `Beta` is genuinely **removed** and `Gamma` is renamed to `Gamma2` + edited. `GITHUB_EVENT_PATH=$SP/hist122/ev-b1g.json node scripts/check-guidance-touch.js --repo-root $SP/hist122/b1_greedy` → exit 1:
   ```
   section "beta"  changed but has no new entry … add "## YYYY-MM-DD — beta — edit"
   section "gamma" changed but has no new entry … add "## YYYY-MM-DD — gamma — remove"
   ```
   `gamma` still exists; complying writes `## <date> — gamma — remove` into the audit trail — **the exact false retirement B1 was raised to stop** — while the section that really was retired (`beta`) is recorded as an edit. On `f6f71b1` the same fixture reported `beta — remove` (right) and `gamma — remove` (wrong); the fix changed which id is wrong, not whether one is.

2. **A new fail-open the previous code did not have.** `$SP/hist122/b1_failopen`, `ev-b1x2.json` — a pre-manifest fork that **splits** `## Security`: the old body moves verbatim under a new `## Secrets` heading and `## Security and secrets` gets completely new text. `lev("Security","Secrets")=3` beats `lev("Security","Security and secrets")=12`, so row `security` resolves to `Secrets`, whose body equals the base body → **exit 0, `no guidance section changed between base and head — nothing to require`** for a diff that rewrote the section wholesale. `f6f71b1` exited 1 on this fixture (wrongly typed, but it stopped the PR).

3. **False red on a pure rename**, which the README says needs no entry. `$SP/hist122/b1_falsered` (`ev-b1x1.json`): pure rename + a nearer new heading → exit 1 demanding an `edit`. And `$SP/hist122/b1_swap` (`ev-b1sw.json`): **two pure renames**, both bodies byte-identical, `Beta`→`Beta and its friends` and `Gamma`→`Gam` — the greedy pass crosses them and both ids are reported as edits, two false reds for a diff that changed no section content at all.

*Reachability:* every one of these needs the manifest **absent** at head or at the merge-base — i.e. a branch forked before `agents-md/eval-coverage.yml` landed (#119), or a branch that deletes it. That window is closing, and the single-row shape the brief specified is genuinely fixed. But B1's named harm is not, and the fix traded a false red for a silent pass in shape 2.

*Recommended fix (minimal, keeps #43 green):* make the approximate match **mutual and unambiguous** — resolve row *R* to heading *H* only when *H* is *R*'s nearest unclaimed candidate **and** *R* is the nearest unresolved row to *H*; leave the rest unresolved. Then, separately, **never emit `remove` for an id whose base-side row was itself fallback-resolved while its head side dropped** — report that as not-checkable (a stale row, `:786`'s existing `continue`) rather than a retirement, so no asymmetry in a *fallback* can write a `remove`. Shape 2 then reverts to the honest "not checkable" rather than a green light. A distance cap alone does not fix shapes 1 and 3.
