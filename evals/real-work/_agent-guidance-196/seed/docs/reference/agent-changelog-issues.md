# Issues filed from the agent changelogs

A loose spec for the GitHub issues opened while writing an entry in
[`agent-claude-code.CHANGELOG.md`](agent-claude-code.CHANGELOG.md) or
[`agent-codex.CHANGELOG.md`](agent-codex.CHANGELOG.md). A target repo's own
`AGENTS.md` wins where the two disagree. The generic form of this spec is the
`vendor-release-impact-issues` skill (`adam-coding-anywhere`). This file adds
fleet detail to it and wins where the two differ, except that it may not relax
the skill's hygiene rules or its title lint. The procedure around it is
[`agent-changelog-routine.md`](agent-changelog-routine.md).

## When to file

- **One issue per change group per affected repo.** A group that touches three
  repos gets three issues, each written for its own repo.
- **Name the surface or don't file.** An issue needs a file, test, doc line,
  setting or pin in the target repo that the change touches. "Might be
  relevant" with nothing named stays out of the changelog entry too.
- **Search first.** Check the target repo's open and closed issues. If one
  already covers the change, link it in the group's **Issues** line instead of
  filing a duplicate.

## Title

`<Agent> [<version or range>] <what changed>: <what it touches here>`. Include
the version when one release carries the change.

For example: `Claude Code 2.1.214 SessionStart reports fork: fleet hooks match
startup|resume`.

- Keep it under about 110 characters.
- Don't put `<placeholder>` text in a title. GitHub stores it, but the GitHub
  MCP server strips tag-shaped text when it reads a title back, so the issue
  looks broken to any agent using that server. Lint titles for `<[A-Za-z/!]`
  and write `NAME` or `N` instead.

## Body, in this order

1. **Lead line.** `Preliminary: found while writing <changelog path>,
   entry <date>, group <N> ("<group title>"), in <PR link>. Not yet verified
   against this repo.`
2. **`## <Agent> change(s)`.** Every quote from the group, exact and oldest
   first. Each is followed by its release-page link and the release's publish
   time (see [Release publish times](#release-publish-times)). Put a quote in
   a ` ```text ` fence instead of a blockquote when it contains anything
   GitHub acts on: `#N`, `owner/repo#N`, `@name`, or an issue, PR or commit
   URL. Every Codex quote qualifies, because of its `(#NNNN)`.
3. **`## Why it may matter here`.** One bullet per affected file, claim, test
   or pin, saying what the change does to it.
   - Write only what you read in the file.
   - Say "may" wherever you have not measured the behavior.
4. **`## To check`.** Checkboxes for:
   - the measurements to take, with the minimum agent version;
   - the docs, tests and pins to update.

   Respect the repo's one-way doors and gates (for example, skill directory
   names, `docs/skill-impact.md`, `docs/guidance-impact.md`, touch gates).
5. **`## If behavior and the changelog disagree`.** The fixed block below,
   verbatim, with `<agent>` and `<Agent>` filled in.
6. **Footer.** `---` and then `_Generated by [Claude Code](https://claude.ai/code)_`.

### Fixed block

```markdown
## If behavior and the changelog disagree

While working this issue, if <Agent> does something the quoted changes don't
describe, or doesn't do what they say:

- Record it in `_agent-guidance`'s
  [`docs/reference/agent-<agent>.DISCREPANCIES.md`](https://github.com/Adam-S-Daniel/_agent-guidance/blob/main/docs/reference/agent-<agent>.DISCREPANCIES.md),
  using the template at the top of that file, via a PR to `_agent-guidance`.
- Read the vendor docs only if the changelog is ambiguous, and quote the
  passage you relied on.
- Link the entry from this issue before closing it.
```

## Release publish times

Every vendor version that this process's own text names carries the release's
GitHub publish time, in UTC to the minute (`YYYY-MM-DDTHH:MMZ`). Text the
process did not author is never stamped or changed.

- **Stamped, because the process writes it:**
  - Quote attributions: `— [v2.1.214](<release URL>), published 2026-07-18T01:20Z`
    under a `>` quote, or `0.146.0 (published 2026-07-29T01:42Z):` above a
    fenced Codex quote.
  - Versions named in the "Why" and "To check" prose.
- **Never stamped:** vendor quotes, text quoted from repo files or docs, issue
  titles, and the lead line's group title, which quotes the changelog file.
- **Mark, don't match.** When drafting, write each version your prose names as
  a marker, `{{2.1.214}}`. The generator renders the first use of each version
  as `2.1.214 [2026-07-18T01:20Z]` and later uses bare. Square brackets let the
  stamp sit inside parentheses.

  Never run a version matcher over finished text. It cannot tell your words
  from a quote, and on 2026-09-25 it put a stamp inside a quoted "2.1.273+".
- **Lint the prose before rendering.** Remove code spans and `"quoted"` spans,
  then any version left unmarked is an error: mark it, or quote it. Match
  `v`-prefixed forms too (`v2.1.275`).
- **Where the time comes from:** the release's `published_at` in the API, or
  the `datetime` attribute of the release page's timestamp. Both are UTC;
  truncate to the minute. The page's visible date is the viewer's local time.
  Don't use:
  - the API's `created_at`, which is the tagged commit's date;
  - the tag's commit time. Claude Code tags land within about a minute of the
    release;
  - the npm publish time. Codex reaches npm 4–6 minutes after the release.

## After posting

Read every issue back with a raw REST `GET /repos/{owner}/{repo}/issues/{n}`,
not with the tool that wrote it. Check:

- the title, exactly;
- the body, against what you generated;
- that the footer is present.

In Claude Code cloud sessions, `mcp__github__issue_write` has reported success
on both create and update while storing the body without its footer. A REST
call through the session proxy keeps a footer, and it needs
`Content-Type: application/json`.

## Hygiene

- **Links:** link vendor release pages only. Put upstream issue references in
  code spans (`anthropics/claude-code#6235`). A link or bare reference posts a
  backlink on the vendor's public issue.
- **Mentions:** put any `@name` token in a code span, or it mentions a user.
- **Closing keywords:** `close`/`closes`/`closed`, `fix`/`fixes`/`fixed` and
  `resolve`/`resolves`/`resolved`, in any case, followed by `#N`,
  `owner/repo#N` or an issue URL, close that issue. This happens when a PR
  whose body contains them merges to the default branch, or when a commit
  whose message contains them lands there. Backticks and fences don't
  neutralize them. Never write one unless closing is intended.
- **Labels:** none required. The fleet has no vendor-change label.

## Closing

- **Completed:** when the checks are done. Link the PR.
- **Not planned:** when the change turned out not to matter. Give one line
  saying why.

Either way, first make sure any discrepancy found is recorded in the
`DISCREPANCIES.md` sidecar and linked from the issue.
