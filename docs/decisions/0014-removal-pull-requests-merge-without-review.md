# ADR 0014: A skill removal pull request merges automatically, with no human review

- **Status:** accepted (2026-10-26); auto mode is wired (second addendum
  below), but both blocks of `evals/gate-policy.yml` commit
  `retirement_mode: proposal` since Adam's 2026-11-03 "Resume, auto-removal
  off", pending his decision on the betting-bound rule (last addendum
  below). In `auto`, a removal merges only once the improvement gate's
  GitHub App secrets are set in skills-evals; until then the workflow falls
  back to `proposal`.
- **Issue:** [#70](https://github.com/Adam-S-Daniel/skills-evals/issues/70)
  (part 2; part 1, the verdict, is
  [#411](https://github.com/Adam-S-Daniel/skills-evals/pull/411)).
- **Deciders:** Adam, directly: "Build it" for automatic removal of
  nonperforming skills (2026-10-25), and, at 23:14 UTC the same day, that
  removal pull requests auto-merge with no human review despite the fleet
  rule, with exception ADRs. On 2026-10-26 he decided results are not
  signed: the gate guards against honest mistakes only.

## Context

The fleet guidance says "PR + auto-merge is not a sanctioned bot-write
path", with named exceptions (skills-evals' roster PR, repo-settings
ADR 0003, recorded here as [ADR 0003](0003-roster-merges-automatically.md)).
adam-agentskills adds its own one-way doors: a skill basename, once shipped,
keys every consumer's `skills.lock` and `setup.sh` links, and a change to one
gets an adversarial round before merge (its `AGENTS.md`, "One-way doors get
an adversarial round").

The eval-loop thresholds design of 2026-10-25 (version 2, kept outside this
repository; its "Decisions for Adam" list) defaulted to "Adam merges; asked on a card". Adam chose the
opposite: a removal the verdict supports should land without waiting on him.
The verdict is built to make a wrong removal unlikely, not impossible: the
run is the unit, cells pool only runs of the content on main, a cell is
`no-benefit` only at two fixed looks (at least ten counted runs per arm),
every fixture on main crossed with every current roster model must be
`no-benefit`, any agent-errored trial blocks it, any benefit keeps, and
compute_gates lets one skill retire per evaluation (harness/gates.py).

## Decision

1. In `retirement_mode: auto`, `scripts/retire_skill.py` opens a removal
   pull request in adam-agentskills and enables auto-merge (merge commit).
   No human reviews it; adam-agentskills' required checks still gate it.
2. It acts only from the scheduled workflow (`GITHUB_EVENT_NAME` is
   `schedule`), never from a dispatch, a pull request or a terminal; auto
   mode also needs `GITHUB_ACTIONS=true` on `refs/heads/main`, and the
   caller must name it (`--allow-mode auto`; the default is `proposal`).
3. At most one removal pull request (head `retire-skill/<skill>`) is open
   at a time; an open one holds the slot whatever the newest verdict says.
4. It refuses a skill whose basename is not found exactly once across the
   registry checkouts it is given, or whose copy is not a real
   `plugins/<plugin>/skills/<skill>/` directory of adam-agentskills (no
   symlink on the path, nothing it writes resolving outside the checkout),
   and a verdict whose cells are not every fixture crossed with every
   roster model exactly once, each `no-benefit`.
5. The pull request carries the whole removal, because nothing human edits
   it before adam-agentskills' required checks read it: the skill directory,
   the plugin's version in both manifests (adam-agentskills ADR 0009; a
   major raise since the second addendum),
   a `docs/skill-impact.md` `remove` entry, the skill dropped from
   `scripts/plugin_layout.json` (the ADR 0013 layout its tests pin), the
   README skill table regenerated by the registry's own
   `scripts/generate_readme_table.py`, and — when `skills.lock` locks the
   plugin — a second commit re-pinning the lock with the registry's
   `scripts/generate_skills_lock.py --repin`, verified with
   `--check-current`. Those two scripts are the registry's own, run from the
   checkout with a scrubbed environment (no token reaches them); this repo
   reimplements neither. The removal is refused rather than left half-done
   when the checkout cannot support it: a shallow clone (the lock reads the
   commit it pins), a skill that is its plugin's last (emptying a plugin is
   a registry decision, which the lock generator refuses too), a layout file
   that does not list the skill, a generator that exits non-zero, a skill
   whose removal the registry's `plugin-runtime-review` gate would hold for
   the owner (auto-merge cannot approve it), a skill a
   `scripts/skills_waivers.yml` waiver covers (the waiver would go stale),
   or a skill defining a test that a tracked source elsewhere cites by name
   (the registry's citation test would fail; removing `skills-doctor` today
   is one, through `.claude/hooks/skills-bootstrap.sh`). A refusal exits 2
   and writes nothing, so the run goes red and a human removes the skill.
6. In `retirement_mode: proposal` (the committed value), a `retire` verdict
   files or updates one skills-evals issue instead, and a human removes.
   One issue per skill, ever: only issues `github-actions[bot]` opened
   count, and a closed one means the skill is already decided, so nothing
   is filed again.
   Switching to `auto` is Adam's call, made in `evals/gate-policy.yml`.

## Consequences

- **This ADR is one of three.** The exception must also be recorded in
  repo-settings (a bot write path that merges into a protected default
  branch, and whatever credential or ruleset change it needs) and in
  adam-agentskills (a removal of a shipped skill without the adversarial
  round its `AGENTS.md` requires of one-way doors). Neither is written
  here; auto mode stays off until both exist.
- **Auto mode needs a credential that does not exist.** The scheduled job's
  own token can write skills-evals issues only. Auto mode needs a GitHub App
  with contents and pull-requests write on adam-agentskills alone, minted
  immediately before use; until it exists the workflow allows only
  `proposal` and exits 2 on `auto`, rather than skipping quietly.
- **A removal is a one-way door in its consumers.** Every `skills.lock`
  that pins the plugin's bundle digest goes stale when the removal merges,
  and must be re-pinned. adam-agentskills' required checks are what stop a
  removal that breaks its own tree; a failed check leaves the pull request
  open, which holds the one slot until a human closes it.
- **Results are trusted as written.** Anyone who can write the results
  branch can make a skill retire; equally, anyone who can merge to
  adam-agentskills can remove one. The gate guards against honest mistakes
  (a changed fixture or skill, errored trials, a copy of a run ingested
  twice), not forgery (Adam, 2026-10-26).

## Addendum (2026-10-26): auto mode wired and switched on

Adam decided on 2026-10-26 that skill and section removal pull requests
auto-merge with no human. `evals/gate-policy.yml` now commits
`retirement_mode: auto` for skills (the one switch; set it to `proposal` to
stop removal pull requests), and `skill-coverage.yml`'s `retirement` job
wires it. The guidance block stays `proposal`: the App below is installed on
adam-agentskills alone, and _agent-guidance has no write path yet.

- **The credential.** The job reuses the improvement gate's GitHub App
  exactly as `routine-improve-gate.yml` mints it (secrets
  `EVAL_IMPROVE_APP_CLIENT_ID` and `EVAL_IMPROVE_APP_PEM`; owner
  Adam-S-Daniel, repository adam-agentskills only, contents and
  pull-requests write), in the step right before the one that uses it,
  under `continue-on-error`. The token reaches `retire_skill.py` as
  `REGISTRY_TOKEN`, used only for adam-agentskills writes; the push sends it
  as an HTTP header through `GIT_CONFIG_*` and is verified by fetching the
  branch back (`git merge-base --is-ancestor`). Issues still use the job's
  own token. With no token (a secret unset, or the mint failed) the script
  gets `--fallback-to-proposal` and files the issue instead of exiting 2.
- **Never through plugin-runtime-review** (adam-agentskills ADR 0021,
  decision 4). `retire_skill.py` reuses `scripts/improve_gate.py`'s
  `auto_refusal`: a skill whose plugin has `hooks/`, `bin/`, a settings or
  package file, or a manifest `hooks` or `settings` key gets the issue, not
  a pull request. Today that is every skill in `adam-coding-local`.
- **One loop pull request at a time** (ADR 0021, decision 5). Auto mode
  opens nothing, and exits 0, while any `eval-improve/*`, `draft-skill/*` or
  `retire-skill/*` pull request is open in adam-agentskills, the slot
  `routine-improve-gate.yml`'s `registry-pr` job checks. Decision 3 above
  counted only `retire-skill/*` heads, and the script exited 2 on one;
  waiting is not an error. A closed
  `retire-skill/<skill>` pull request means a person declined the removal,
  so none is opened again, as a closed issue decides a proposal.
- **The pull request.** Ready, labeled `agent-authored`, its body ending in
  the fleet's agent marker (`<sub>🤖 Written by Claude Code on behalf of
  @Adam-S-Daniel</sub>`) and its commits in an `Agent: claude-code` trailer,
  as the improvement gate's are; auto-merge is enabled with a merge commit
  and `--match-head-commit`, then read back, and a label or auto-merge that
  did not take fails the run with the pull request left open.
- **A major version.** A removal breaks every consumer that calls the
  skill, so the plugin's major version is raised (the registry's
  `check_plugin_versions.py` asks only for a raise; it bumped
  `adam-coding-local` 1.1.0 -> 2.0.0 when it removed `sync-skills`).
- **The skill-impact entry** follows the registry's entry format: dated the
  day the workflow runs (`--date`, the gates file's `as_of` when absent),
  links in full, the version bump, the pooled run count and fixture paths
  as the `Eval:` line, and `pending merge` as the outcome.
- **The private registry.** adam-agentskills-private
  (`Adam-S-Daniel/adam-agentskills-private`) is never a target
  (adam-agentskills ADR 0021, decision 7). The job does not check it out,
  so a skill there has no tested digest and never reaches `retire`, and in
  auto mode a copy found outside adam-agentskills is refused.

Still open: the repo-settings exception ADR this record asks for; the App's
two secrets in skills-evals (until both exist every removal is an issue); and
`skills-doctor`'s removal stays refused while adam-agentskills'
`.claude/hooks/skills-bootstrap.sh` cites its test

## Addendum (2026-11-02): one removal rule, notified and reversible

Adam decided on 2026-11-02 (#557) that skills and guidance sections share
one removal rule: a removal when the gate is 90% confident that the subject
does not improve results by 0.15 or more (`retire_confidence` 0.90,
`objective_margin` 0.15, `judge_margin` 1.5), with no separate confirmation
step, in both blocks of `evals/gate-policy.yml` (#565). Keeping stays at
85%, applied per subject across its cells and routes (#578). Both blocks
commit `retirement_mode: auto`; the 2026-10-26 addendum's "the guidance
block stays `proposal`" no longer holds, since the eval-improve App now has
a write path to `_agent-guidance`.

What makes a removal with no human safe enough is that it can be undone:
every removal pull request is followed by an `agent-authored` notice issue
in skills-evals that mentions Adam, links the pull request and says how to
reverse it (close it before it merges; press Revert after), and the
explorer lists every removed skill and section with its date and that link
(#565, #567). The trade Adam accepted: with no confirmation step, a section
that helps only beside today's guidance but not beside older versions can
be removed (43-97% of the time in the simulation of #565); the notice and
revert are its backstop.

## Betting-bound addendum (2026-11-03)

A statistics review of the gate on 2026-11-03 found the removal bound
invalid at the run counts where it decided. It was a normal-mixture
confidence sequence over run means whose variance came from a prior, so
four identical runs per arm read as certainty and removed a skill, and a
subject that helped by exactly the margin was removed 15-53% of the time
against a 5% target. It also found that cells at the ceiling decided
removals they could not show, that a guidance section's older strata were
weighted toward removal, and that the judge, having to agree to a removal,
blocked it for good wherever its call was skipped. Adam turned removals to
proposals that day ("Resume, auto-removal off"). A threshold sweep the same
day simulated replacements on the real outcome shapes. What
`harness/gates.py` now does, with the levels the sweep chose:

- The bound is a betting confidence sequence on the paired per-fire
  difference D = with minus without (Waudby-Smith and Ramdas, aGRAPA bets
  capped at 0.9 of the safe stake). It needs no variance prior and is valid
  at every pair count.
- Keep when the subject's keep test shows D above 0 at 80%, the alpha split
  over its cells (Bonferroni). A cell shows no benefit when its test shows
  D below 0.15 at 90%. Removal is the silent, unchecked error, so it keeps
  the stricter level.
- A cell whose without arm a betting bound at 90% shows above 1 minus
  the margin is `ceiling`: it does not vote, the planner stops firing it
  and asks for a harder fixture (without blocking the subject's other
  cells), and a subject whose every cell is at the ceiling is `ceiling`. A
  harm test (D below 0 at 90%) runs wherever the without arm is high, so a
  cell the skill makes worse is `no-benefit`, never hidden as a ceiling.
- A cell undecided after 40 pairs is `no-clear-effect`.
- The judge is reported and does not vote, and single checks no longer
  keep on their own.
- Cells decide on current content only: for a guidance section, the runs
  beside the current rest of the guidance. Older strata are ignored.
- The first bet starts from a prior learned from other subjects' earlier
  pairs, which changes how soon a cell decides but not the bound's level.

What this addendum changes about removal: **an automatic removal needs at
least two cells with headroom, every one no-benefit.** A `retire` verdict
with one headroom cell, with any `no-clear-effect` cell, or with any
`ceiling` cell, carries `removal: proposal`, and `scripts/retire_skill.py`
files the issue for it even in `auto` mode; it re-derives the mode from the
cells and lowers a gates file whose `removal: auto` the cells do not
support. A broken-fixture cell may stand beside a removal, but at least
one cell must have headroom. The 2026-11-02
addendum's per-route keep and its 85% level are superseded, as is its
note that both blocks commit `auto`. Whether removals go back to `auto`
under this rule, or stay proposals only, is Adam's decision, still
pending; `retirement_mode` stays a policy knob at `proposal` until he
makes it.

### Adversarial round 1 (2026-11-03)

An adversarial review of the change before merge found that a ceiling was
judged on a sample mean over three pairs, so three perfect pairs parked a
cell for good and let two flat cells remove the subject automatically. A
cell is now `ceiling` only when a betting bound on the without arm's run
means, at the remove level, shows the mean above 1 minus the margin (at
least 18 pairs at 1.0, 25 at 0.95; 0.90 does not reject inside the cap),
and any retire verdict that includes a ceiling cell is a proposal. A harm
test at high cells keeps a harmful cell from hiding as a ceiling. The
planner no longer lets a parked cell block its subject, and the cheaper
model no longer holds the dearer one when the cheaper cell is stuck.
Known limits it left:

- *Late arrivals and prior refits re-sort a cell* (m2). A cell is
  re-classified over every run each evaluation, so a run ingested late, or
  a bet prior refit on newer results, can move the pair at which a test
  rejects and so its class. Each evaluation is still a valid test at its
  level, and the seeded simulations' rejection rates stay under alpha, but
  the sequence of verdicts a cell shows over time is not itself one
  sequential test.
- *In-situ guidance errored trials do not block* (m5). A guidance cell's
  agent-errored trial scores 0 and does not keep the cell from removal, as
  a skill's does: the section is measured beside the whole guidance, where
  an agent failure is part of the outcome. It is a deliberate asymmetry, not
  a guarantee that errors only help keep.
- *Each guidance edit resets the evidence* (m6). A cell decides only on runs
  beside the current rest of the guidance, so an edit to any other section
  starts every in-situ cell over. A frequently edited guidance file may
  never let a section accumulate the 18 or more pairs a decision needs.
- *The current keeps restart as insufficient* (m7). The 8 subjects kept
  under the old bound (4 skills and 4 guidance sections) had 1 to 3 pairs
  per cell. A valid bound needs 4 to 17 pairs to keep, depending on the
  effect size, and 18 to remove identical arms, so each returns to
  `insufficient` and is measured again rather than carrying a keep the new
  bound cannot support.
